  v8.01（2026-07-01）複数選択・水平垂直ドラッグ・レーン色・デザインテンプレート・おしゃれステップ図
  ──────────────────────────────────────────────────────────────────────────────

  背景・目的:
    ①選択とドラッグの操作性を一般的な作図ツール（PowerPoint 等）に合わせたい、②レーン色を
    後から手軽に変えたい、③図の「色は変えずに見た目（角丸・線・影）だけ」を一括で整えたい、
    ④画像で示された番号サークル/矢羽/ピルのようなインフォグラフィック調のステップ図を作りたい、
    というユーザー要望。①〜③は明確なので即実装、④は見た目主体のため事前にHTML/SVGモックで
    複数案を提示し、採用テンプレを決めてから実装した。

  設計上の判断（落とし穴と対策）:
    ・修飾キーの役割を「押した瞬間」に確定させない。従来は Ctrl+mousedown で即複製していたため、
      Ctrl+クリック＝複数選択と両立できなかった。対策＝mousedown では通常ドラッグを仕込むだけにし、
      「クリック確定(mouseup・未移動)＝選択トグル」「ドラッグ確定(mousemove・4px超)＝Ctrlでコピー化
      (convertDragToCopy)」に振り分けた。convertDragToCopy を必ず S_didDrag 成立後に呼ぶ点が肝
      （指の微揺れで誤コピーしないため）。Ctrl/Shift どちらのクリックでも複数選択できる。
    ・Shift+ドラッグの水平/垂直固定は、mousemove 冒頭で pt を制約（変位の大きい軸だけ残す）すると
      下流の全分岐（group / 自由配置 / レーン）に一括で効く。ただし整列・グリッド・レーン内吸着が
      固定軸を動かしてしまうので、S.drag.constrained のとき該当軸のスナップを無効化して軸を純粋に
      固定する。
    ・デザインテンプレート（S.style / STYLES）は「色（各シェイプの fill/stroke・レーンの bg/hd）は
      一切変えず、形の装飾（角丸rx倍率・線幅・影フィルタ・アクセント帯・矢羽/ピル形状）だけ」を
      差し替える方針。shapeEl の rx を styRx()、線幅を stySW() 経由にし、影とアクセント帯は
      renderNodes で shapeEl の戻り要素へ後付け（テキストに影を掛けない）。矢羽/ピルは基本の
      「プロセス(rect)」の形のみ差し替え（他 rect 系は角丸だけ変化）＝ガント等を壊さないため。
      影は SVG フィルタ（ds-*）を defs に静的定義。保存/復元に S.style・S.stepNums を追加。
    ・おしゃれステップ図: 番号サークルは新シェイプ step_num（円＋大きな01/02/03＋下にラベル）。
      番号は「読み順（横広がりなら左→右／縦広がりなら上→下）」で毎描画時に自動採番（stepOrder）
      するため、並べ替え・追加で番号が自動で振り直る。番号バッジ(S.stepNums)は一般のプロセス系
      シェイプ左上にも同ロジックで付与。配色テーマは作成済みシェイプへ色を上書きする明示操作
      （Ctrl+Z で戻せる）＝既定方針「色は変えない」の任意的な例外として提供。レイアウト挿入は
      既存の addNode/addEdge 相当で編集可能なノード列＋接続線を生成（挿入後もドラッグ/文字編集可）。

  既知の注意:
    ・デザインテンプレートと配色テーマは図全体（全図種）に効く（S.style はグローバル）。矢羽テンプレは
      「プロセス(rect)」のみ形が変わる。step_num は自由配置シェイプ扱い（レーンに拘束されない）。

  追補（v8.01 同セッション・版番据置）:
    ・レイアウト挿入を縦横モード追従に変更。挿入時 isV() を見て、縦モード＝上→下の列／横モード＝
      左→右の行で並べる。挿入後に向きを切り替えても toggleOrientation の全ノード x↔y 入替で列ごと
      回転する（番号は stepOrder が読み順を再判定して追従、番号サークルのラベルは縦並び＝円の右／
      横並び＝円の下へ _flowDirs で自動切替）。
    ・ステップ数を可変に。挿入した列を flowId で1グループとして管理し、列末尾に＋（flowAddStep＝末尾へ
      1つ追加・並び方向を継続）／－（flowRemoveStep＝末尾を1つ削除・最低1つは残す）ボタンを描画
      （renderFlowControls）。ボタンは選択モード時のみ表示し、class="flow-ctrl" を付けて
      buildExportSvg のクローンから除去＝SVG/PNG/PDF には出さない。


  背景・目的:
    建設・土木の施工工程表（バーチャート式）は、用紙上部に 工事名・工事場所・発注者・
    施工者・工期・担当（現場代理人等）・作成日・版数 を載せ、右上に承認（作成・確認・承認の
    押印）欄、下部に凡例を置くのが定番。これまでガントは時間軸ヘッダー(2段)しか無く実務の
    工程表として提出しづらかった。Web調査で項目名・配置の定番を確定した上で実装。現場ごとに
    記載項目が異なるため「自由な行（ラベル：値）の追加・編集・並べ替え」でカスタマイズ可能に。

  設計上の最重要判断（落とし穴と対策）:
    画面の当たり判定は全箇所 (clientY - rect.top)/zoomLevel のピクセル換算で、SVGの viewBox
    オフセットを考慮していない（例: クリック無視ガード if(py<GANTT_HEADER_H)、ganttSlotIndexAtY）。
    そのため「エクスポートで既に使っている負Y方向 viewBox 帯」を画面にも使うとクリック位置が
    全部ズレる。
    → 採用方式: 見出しを “上部の非操作ストリップ（正Y空間 y:0..ganttHeadH()）” として描き、
      時間軸ヘッダー・グリッド・行を見出し高さぶん下げる。下げ量を ganttBodyTop()
      （= ganttHeadH() + GANTT_HEADER_H）に集約し、「内容の上端＝GANTT_HEADER_H」だった参照を
      これに一括置換。時間軸ヘッダー(renderGanttHeader)は内部座標を一切変えず translate グループで
      平行移動（DOMイベント＋svgPt はそのまま効くので＋ボタン・列幅リサイズも不変）。
      これらをライブSVGへ描くので buildExportSvg のクローンにそのまま乗り、SVG/PDF出力が自動追従。
      画面の座標系は従来どおり「ユーザー単位＝ピクセル・原点0」を維持＝当たり判定は上端定数の
      差し替えのみで済む。

  レイアウト確定（モック反復でユーザーと合意）:
    工事名（大）＋情報を左に2列・下詰め（本体との余白を詰める）／右上に作成日＋承認欄（小さめ・
    画面の並びは左→右で承認・確認・作成＝紙面では右から作成・確認・承認）／凡例は「押印欄の下・
    右側ゾーン内」で横長（3列×2段）・角丸の黒枠で囲む（説明欄の下には侵入させない）。
    見出しの高さは行数・承認ON/OFF・凡例項目数で自動可変（ganttHeadModel が縦寸法のみ算出、
    横位置は描画時に SVG_W から右端基準で決定）。

  データモデル / 永続化 / 後方互換:
    S.gantt.header = {show,title,rows:[{label,value}],showDate,approval:{show,slots:[承認,確認,作成]}}
    S.gantt.legend = {show,auto,overrides:{key→ラベル上書き},extra:[{label,color,stroke}]}
    approval.slots は「描画順＝左→右」で格納（紙面で右から作成のため、表示時に右寄せ配置）。
    保存は saveHtmlCore が S.gantt 全体を JSON 化するので追加フィールドも自動で永続化される。
    旧ファイル（header/legend 無し）は描画前に ganttEnsureHeader() が既定補完＝そのまま開ける。

  凡例の自動生成:
    ganttLegendItems() が S.nodes を走査し、使われている要素だけを拾う＝タスク（予定）／進捗
    （progress>0 のとき）／マイルストーン／フェーズ／休工（suspensions 有り）／土日。色見本は
    SD.gantt_* の fill/stroke を参照（図と完全一致）。overrides でラベルだけ差し替え、extra で
    「電気設備（協力会社）」等の工種・業者色分けを手動追加できる。

  エクスポート反映:
    ・SVG/PNG: ライブSVGに描くのでクローンに自動で乗る。見出し表示時は buildExportSvg の図面名
      タイトル帯を省略（工事名と二重化しないため）。
    ・PDF: 表題＋時間軸ヘッダーを <thead> に内包し各ページ先頭で繰り返す（viewBox を 0..ganttBodyTop()
      に拡張）。本体はフェーズ境界で改ページ（従来どおり）。図面名帯は見出し表示時は出さない。
    ・Excel: 帯(BAND)を「1 + 見出し情報行数」に拡張し、行1に工事名＋作成日、続く行に情報2列、
      （承認ONなら）承認欄をテキストで展開。最下部に凡例（色塗りセル＋ラベル）を1行追加。
      freeze/printTitlesRow は時間軸のみ繰り返す既存挙動を踏襲（情報帯は1ページ目先頭のみ）。

  既知の注意:
    ・見出し表示時は calcCanvasSize で SVG_W を最低 1120px 確保（狭い図でも右ゾーン＝承認欄＋凡例が
      重ならないように）。
    ・設定UIの動的リスト（行・承認・凡例）はテキスト入力にフォーカス中は作り直さない（ganttHeadEditing
      ガード）＝入力中のキャレット/フォーカスを維持しつつ SVG だけライブ更新。

  検証（Claude_Preview 実DOM ＋ node --check）:
    headH＝承認OFF:164／ON:176、行数で追従。bodyTop=232 でクリック→正しいタスクindex、
    header OFF で bodyTop=56（＝完全に従来挙動・回帰なし）。設定UI＝行の追加/削除/▲▼並べ替え・
    承認トグル・凡例ラベル上書き・工種色分け追加が即反映。保存→JSON→復元ラウンドトリップで
    header/legend 保持。旧形式（header/legend 無し）も補完して描画。buildExportSvg は工事名を内包し
    図面名帯の二重化なし（nameBand=0）。PDF/Excel いずれも例外0で生成（Excel 13.8KB 出力確認）。
    全インラインスクリプトの node --check ＝SYNTAX_OK。

  （diagram_v7.11.html をコピーして diagram_v8.00.html を新規作成。<title>／#app-title-bar／serve.js 既定
    配信先を v8.00 に更新。大変更＝整数部を v8 に。次の小変更は v8.01。）

    検証（Claude_Preview 実DOM）: 削除＝ホバー表示/確認後に列とcells破棄・c0は非対象。表示＝

■ 左サイドバー（編集バー）にスクロールを追加
  why: 見出し・凡例パネルが縦に長く（工事場所等の情報行＋承認欄＋凡例）、画面が低いと
       下側のコントロール（承認欄・凡例設定など）が画面外に隠れて操作不能になっていた。
  how: #app-header（図の名称欄）は固定のまま、その下の全セクション（シェイプ〜レーン）を
       #sidebar-scroll でくくり、flex:1 + min-height:0 + overflow-y:auto で縦スクロール化。
       ヘッダーは常時見える＝図の名称をいつでも編集できる。

■ 見出しの「工事名」を図の名称に一本化（見出し専用の工事名入力を廃止）
  why: 「工事名」と「図の名称」を二重入力させていた。実質同じものなので二度手間・不整合の元。
  how: 見出しパネルの工事名 input（gh-title）を撤去。renderGanttTitleBlock と Excel 出力の
       工事名は exportDiagramName()（＝S_diagramName＝上部「図の名称」）を参照。図の名称欄の
       oninput を onDiagramNameInput() に変更し、ガント＋見出し表示中は即 render() で
       タイトルをライブ追従。h.title は不参照（旧保存データの title は無視・後方互換で実害なし）。
  検証: Claude_Preview 実DOMで、図の名称編集→見出しタイトルが即時更新／工事名入力欄が消滅／
        サイドバーが scrollHeight>clientHeight でスクロール可／console エラー0 を確認。

【v8.02】スイムレーン等の接続線を改良（ラベル線上化・○ホバー化・終点整形・段違い） 2026-07-01
--------------------------------------------------------------------------------
■ 発端（ユーザー指摘・4点）
  ① 接続線のラベル/編集欄が線上に出ない（端点の直線中点＝折れ線から浮く）。
  ② ラベル無し線の○（追加ボタン）が常時表示でうるさい。
  ③ 1つの相手に加えて2つ目へ繋ぐと、扇状分散で1本目の始点がずれてL字に曲がる（真下なのに斜行）。
  ④ 3つ目へ繋ぐと2本目と3本目の横線が同じ高さで重なる。

■ 仕様決定（AskUserQuestion で合意・モックで反復）
  ・始点(出口)は等間隔(扇状分散)のまま許容。終点は「一直線にできる線は一直線を優先(端が中央で
    なくても可)／できない線は辺の中央に着地」。相手シェイプごとに判定を変える。
  ・重なり回避は「曲がる高さ(横トラック)を枝ごとに段違い」。ただし素直に段違いにすると外側の枝が
    内側の枝の横線を突っ切る＝クロスが出る（ユーザーが不可）。
  ・角丸など線の描き方は現行維持（今回いじるのは経路の座標＝frac と段違い位置だけ）。

■ クロスを出さない段違いの原理（重要・why）
  出口辺を共有する“曲がる線”を、相手までの距離が【近い相手＝相手寄り(下段)／遠い相手＝始点寄り
  (上段)】のトラックに置く。こうすると各線の縦の降り口は自分のトラックまでしか下りず、遠い相手の
  長い横線は近い相手の短い横線より上を通り、互いの縦線が相手の横線を突っ切らない＝交差も重なりも
  出ない（源が箱幅より広く相手が横に散る配置でも成立）。逆順(遠い=下段)にすると必ず交差する。

■ 実装（diagram_v8.02.html）
  ・allocatePorts 末尾に段違いパスを追加（['swimlane','flowchart','bpmn'] のみ対象）。
    出口辺ごとにグループ化→各線の出口X/Yを算出→終点 entryFrac を直線化(範囲内なら exitに一致)／

【v8.06】2026-07-21 — ガント「時（1時間ごと）」モード追加
================================================================================
■ 目的・経緯（why）
  ・ユーザー要望「ガントに1時間当たりの工程モードを追加。ただし既定は従来どおり1日モード」。
  ・仕様は着手前にモック提示＋質問で確定：24時間通し／複数日OK／1時間刻み（分は常に:00）。
    → 稼働時間帯の絞り込みや夜間スキップは行わず「連続タイムライン」を採用。日モードの比例配置
      ロジックをそのまま1時間解像度へ落とすだけで済み、実装リスクを最小化できるため。

■ 設計判断（how）
  ・日時の持ち方: タスク/マイルストーンの startDate/endDate/date を、日モード等は従来の
    `YYYY-MM-DD`、時モードでは `YYYY-MM-DDTHH:00` に拡張。時刻なしは 00:00 とみなす（後方互換）。
    → S.gantt に新フィールドを足さず scale:'hour' だけで表現。snap/restore/init/import は
      既存の Object.assign(defaultGantt(),…) 経由で自動 round-trip、旧ファイルも無改変で開ける。
  ・コアは ganttParseDate の正規表現に任意の時刻部を追加し、書き込み側だけ scale 対応の新関数
    ganttFmt(d,scale) を通す（ganttFmtDate は日付のみのまま据置＝日付入力欄・週/月原点整形を壊さない）。
    ganttAddUnit/ganttDiffUnit に hour 分岐、ganttXToDate を ganttFmt 化。
  ・終了時刻は「排他」に決定（例 9:00〜12:00＝3時間ぶん・12:00 の格子で終端）。日モードの
    「終了日+1日（包含）」とは意味論が異なるため、calcGanttPositions・フェーズ帯・Excelバーの
    3か所で時モードのみ +0（排他）に分岐。モックで提示した見え方（9〜12＝3枠）と一致させた。
  ・編集ダイアログは時モードのときだけ日付入力を datetime-local(step=3600) に切替え、
    保存時に分を :00 へ丸める（ganttInputVal / ganttNormInput）。
  ・Excel: サブ列構築に hour 枝（1時間＝1列・上段=日付/下段=時）。colDateIdx は時刻対応 parse で自動追従。

■ 既知の制約（注意）
  ・休工期間(suspensions)は日単位のまま（編集は type=date を維持、内部の +1日 計算も据置）。
    時モードでも休工は「日」粒度で穴が空く。実害は限定的と判断しスコープ外とした。
  ・既定の完了日は月末(日付)のため、時モードに切替えると 24h×日数ぶん（最大数百列）に広がる。
    重い場合は「完了日」を絞る運用。Excel はサブ列 CAP=500 で保護。

■ 検証（how tested）
  ・追加パッケージ不要（npm レジストリはポリシーで 403）。プリインストール Chromium を
    CDP + Node22 組込み WebSocket で駆動し実機確認：
    既定=日モード／時へ切替(colW=24)／9:00〜12:00 タスクが3列幅で描画／ヘッダー上段=日付・下段=時／
    ganttXToDate 往復一致・時差=3／編集ダイアログが datetime-local／日モードへ戻して回帰なし／
    Excel 出力(時モード)が例外なく完了。全工程で console エラー 0。

【v8.06 追補】2026-07-21 — 印刷(PDF)の時間軸ヘッダーが2ページ目以降に出ない不具合を修正
────────────────────────────────────────────────────────────────────────────────
■ 症状: ガント/工程表の「印刷」出力で、日付・時間の時間軸ヘッダーが1ページ目にしか出ず、
  2ページ目以降はタスク行だけになる。時/日/週/月すべてのスケールで再現（縦方向のページ分割の
  問題のためスケールに依存しない。v8.06 の新機能が原因ではなく従来からの印刷処理のバグ）。
■ 原因(why): 印刷用HTMLは工程表ヘッダーを <thead>(display:table-header-group) に入れて各ページ
  先頭で繰り返す設計。ところが本体(タスク行)を <tbody> の巨大な単一 <tr> にしていたため、
  1つの <tr> が用紙高さを超えて分割されると <thead> が再描画されない（thead の繰り返しは
  「行と行の境目」でしか起きず、単一行の途中改ページには効かない）。フェーズ無しの図では全タスクが
  1 <tr> になり必ずこの状態になる。
■ 対策(how): expPDF のガント分岐を再構成。
  ①各ページ先頭で繰り返すのは「時間軸＋列見出し」だけに限定（表題部＝工事名/図面名帯は pg-once で
    表の外側に一度だけ描き、1ページ目のみ表示）。ユーザー確定＝2ページ目以降は時間軸のみでよい。
  ②本体を「フェーズのまとまり＝1<tr>」または「フェーズ外タスク＝1ページ相当の高さごとのチャンク＝1<tr>」に
    分割。改ページが必ず行境界で起きるようになり、<thead> が全ページ先頭で再描画される。
    ※各 <tr> は SVG 全体を1回直列化するため、当初「1タスク=1行」にしたら直列化がタスク数の二乗コストになり
      printToPDF が固まった（実ブラウザ印刷でも同様）。そこでチャンク高さ maxChunkPx=(W/倍率)×0.7 でまとめ、
      直列化回数をページ数程度に抑えた（W=チャート幅・倍率＝印刷倍率。横長チャートはチャンク大＝ページ少、
      行が支配的なら小＝ページ毎に分割されヘッダー反復。0.7=A系横向きの縦横比を下限に）。
  ③フェーズの切れ目では pg-break(page-break-before) で必ず改ページ（フェーズは途中で分割しない。
    フェーズ名の見た目を保つ。ユーザー確定）。末尾の空き行は従来どおり印刷しない。
■ 既知の注意: 1フェーズが1ページ高さを超える稀なケースは、そのフェーズの2ページ目にヘッダーが
  出ない（フェーズを途中分割しない方針の副作用として許容）。ヘッダーは全幅を用紙幅に合わせる関係で
  縦に圧縮されるが、これはページ1も同条件（従来からの挙動。必要なら印刷倍率を上げる）。
■ 検証(how tested): npm 不可のためプリインストール Chromium を CDP+Node22 WebSocket で駆動し、印刷用HTMLから
  実 PDF を生成→PDFビューアでページ2以降を目視。フェーズ無し(時/日/週/月)＝全ページ先頭に時間軸ヘッダーが
  反復・表題部は1ページ目のみ。フェーズ有り＝各フェーズが自ページ始まり・ヘッダー反復・フェーズ色帯/名は保持。
  thead スライスを単体描画し濃色帯＋日付＋時刻(0〜23)が正しいことも確認。印刷HTMLは0.4〜0.6MBで固まらない。

【v8.07 追補】2026-07-22 — 印刷(PDF)のページ分割を「フェーズ毎に必ず改ページ」→「途切れる時だけ改ページ」に戻す
────────────────────────────────────────────────────────────────────────────────
■ 経緯（why）: v8.06追補で入れた「フェーズの切れ目で必ず改ページ(pg-break=page-break-before:always)」が
  ユーザーの意図と異なっていた。本来は「基本は極力1ページにまとめ、フェーズがページ境界で途切れる場合だけ改ページ」
  （＝従来仕様）が望ましい。ユーザー指示によりバグ修正として直接 main へ反映（版番据置の追補）。
■ 対策（how）: 2段構え。
  (a) expPDF のフェーズ<tr>への強制改ページ(pg-break=page-break-before:always)を廃止（phaseBreak を false 固定）
      ＝フェーズ毎に必ず改ページするのをやめ、基本は1ページにまとめる。
  (b) ただし pg-break を外しただけでは、1フェーズが用紙高さを超えると<tr>が途中で分割され、<thead>の日付
      ヘッダーが2ページ目以降で反復されず消える（v8.06追補の元バグと同じ構造。当初の追補はここが不完全だった）。
      そこで flushPhase を修正し、フェーズの<tr>も maxChunkPx(≒用紙1ページ)ごとに分割 emit（while ループ）＝
      全<tr>が用紙高さ以下になる。
  結果、強制改ページはせず（page-break-inside:avoid でフェーズ/チャンクがページ境界で途切れる時だけ改ページ）、
  かつ各<tr>が用紙以下なので <thead>(table-header-group)が全ページ先頭で反復し日付ヘッダーが消えない。
  <thead>の全ページ反復・チャンク分割・表題部1ページ目のみ(pg-once)は v8.06追補のまま。未使用化した CSS
  ルール .pg-break は残置（無害・コメントで不使用と明記）。
■ 検証（how tested）: 構文チェック(script 2本・エラー0)。プリインストール Chromium を CDP+Node22 WebSocket で
  駆動し印刷HTML/PDFを生成して確認：thead に日付ヘッダー(SVG height=56)を含む／大フェーズ(タスク50)で本体が
  6ブロックに分割され各<tr>高さ≤1584(=maxChunkPx・用紙1ページ相当)以下／pg-break 付与0／--print-to-pdf で
  2ページPDF生成。各<tr>が用紙以下のため <thead> が全ページ反復＝日付ヘッダーは全ページに出る。
  ※headless環境に pdftoppm 不在のため PDF の画素目視は不可。構造・高さ・ページ数で保証（実機の印刷プレビュー推奨）。

【v8.07 追補②】2026-07-22 — 印刷(PDF)の時間軸ヘッダーが2ページ目以降に出ない不具合を「実機PDF目視」で再修正
────────────────────────────────────────────────────────────────────────────────
■ 経緯（why）: v8.06追補・v8.07追補で「各<tr>を用紙1ページ以下に分割すれば <thead>(display:table-header-group)
  が全ページ先頭で反復する」という前提で対策したが、ユーザーから「2ページ目以降にヘッダーが出ない」と再報告。
  当時の検証は構造・高さ・ページ数のみ（PDF画素目視は不可と明記）で、実際の印刷結果を見ていなかった。今回、
  プリインストール Chromium(Playwright) で実PDFを生成し各ページを画像化して目視した結果、前提が2点で崩れて
  いたことを特定した。
■ 真の原因（root cause）: 2つが重なっていた。
  (1) チャンク高さ係数が用紙に対して過大＝ヘッダー分を差し引いていなかった。maxChunkPx=0.7×W/倍率 は
      A/B系横向き(内容比≒0.707)でレンダ高≒0.7×内容幅。各ページ先頭で反復するヘッダー(≒13mm)が上に載ると
      「ヘッダー＋1チャンク」が用紙(≒190mm@A4横)を僅かに超過し、その<tr>が用紙をまたいで分割→続きページで
      <thead>が反復されず消える。※実PDFで再現（p2のみヘッダー、p3〜はヘッダー無しで本体だけ）。
  (2) 【本命】要素数の多いガントSVG(≈860要素の時間軸ヘッダー slice)を <thead> に直接置くと、各<tr>が用紙
      以下でも Chromium が2ページ目以降でヘッダーを反復描画しない。＝(1)を直しても(0.60へ下げても)ヘッダーは
      p2のみのまま。単純図形の placeholder SVG に差し替えると全ページ反復する／同じ複雑さの本体SVGは通常フロー
      なので各ページ正常描画される→「複雑SVGを反復<thead>に置く」こと自体が引き金と切り分け。<defs>(filter6/
      marker15)を除いても再発したため、特定要素ではなく要素規模/描画コストに起因する Chromium 側の挙動。
■ 対策（how）: 2段構え。
  (a) チャンク上限を是正: maxChunkPx=Math.max(300,(W/倍率)×0.60−headerPx)。反復ヘッダー高さ(headerPx=

■ なぜ（why）
  ・①折り返し: 時間軸が常に右へ一直線に伸びるため、工期が長いと横に延々とスクロールし、A4に収まらない／

  ・②点線: 土日祝の網掛け（v8.07）はあるが、その上をバーが素通りするため「この工程は休日を含んでいる」ことが
    図から読めない。実際の稼働日を図で判断できるようにする。

■ 設計判断（why this way）
  ・折り返しの実装方式＝「段ごとに軸原点を段の先頭へ差し替え、Yは平行移動グループでずらす」。
    これにより既存の renderGantt*（行背景/グリッド/軸ヘッダー/左列/バー/フェーズ）をそのまま再利用でき、
    段対応版の関数を二重に作らずに済む。座標計算は常に「段0のローカル座標」で書ける。
    → ganttAxisOrigin / ganttTotalUnits を _gwBand で切り替え、ganttLayer(id) が段ごとの
      <g transform="translate(0,dy)"> を返す。
  ・許す組み合わせを「列が段の境界にぴったり揃うもの」に限定した（時→日ごと／日→週ごと・月ごと）。
    週/月目盛りは1列が粗く境界に揃わないため対象外。これは v8.07 で週/月の休日グレーアウトを非対象にしたのと
    同じ理由で、仕様の一貫性を保つ判断。
  ・週ごとの帯境界は「日曜始まり」（ユーザー指定）。一方 scale==='week' の目盛り自体は従来どおり月曜基準の
    ままにした（既存図の後方互換を壊さないため）。※注意点として下記に再掲。
  ・段をまたぐバーは矢羽根（chevron）で継続を示す（ユーザー選択）。単純に切ると「そこで終わった工程」に見える。
  ・②の分割は既存の ganttBarSegments（休工でバーに穴を空ける仕組み）を拡張して実現。休日判定も既存の
    ganttDayIsHoliday を再利用し、画面のグレーアウトと必ず同条件になるようにした（設定が1箇所で済む）。
  ・休工＝バーを消す表現／休日＝バーを破線にする表現。役割を分けたので視覚的に競合しない。
  ・バーを rect から path 描画に変更した理由: 休日で区間分割すると rect の rx=4 が内側の継ぎ目にも効いて
    「数珠つなぎのピル」に見え、1本の工程として読めなくなる。端の形を左右別に指定できる path
    （0=平ら/1=角丸/2=矢羽根）にし、塗りと外周線を分けて内側の継ぎ目には線を引かない構成にした。

■ 既知の注意（gotcha）
  ・週ごと折り返しの帯境界は日曜基準、scale==='week' の目盛りは月曜基準。両者は別物なので混同しないこと。
  ・折り返しONでは末尾の空き行を1行だけにしている（段ごとに8行の空き行が繰り返されて縦に膨れるため）。

    Excelは横スクロールが自然にできるため実害が小さいと判断し、出力時にヒントで明示する形にした。

■ なぜ（why）

  ・折り返し単位を「目盛りより1段上」で通した: 週→月ごと、月→年ごと。月目盛り＋月ごとは1段1列で無意味なため
    年ごとを採用（ユーザー確認済み）。
  ・週目盛り＋月ごとは列が割り切れない（1月≒4.43列）。当初は「週が月をまたぐから境界に揃わない」と考えて

    **列は切り上げて描き、段の内容を区間の終わり（月末）でクリップする**方式にした。
    - クリップ: clipPath を段ごとに作り、平行移動グループに clip-path を付ける（ganttBandClipId）。
      グリッド・ヘッダー・行背景の個別クランプを全部書くより、はみ出しを1箇所で確実に止められる。
    - バーの切り位置も ganttBandEndX（＝区間の終わり）にした。ceil列の余白に次の月のバーが漏れないため。
    - ヘッダー上段は endX を ganttBandEndX にし、さらに幅0セルを描かないガードを入れた（クリップだけでは
      段の右端に次区間のラベルが半分残る）。**このガードは折り返しON時のみ**にしている＝折り返しOFFの
      描画を v8.07 と完全一致に保つため（OFFで有効にすると月スケールで要素数が2個減って一致しなくなる）。
  ・行間引きで段の高さが段ごとに変わるため、段モデルを「i*固定高さ」から ganttBands()=[{i,dy,H,layout}] の
    一覧方式に作り直した。段ごとに ganttRowSlots(keepIds) で行を絞ったレイアウトを持たせる方式にしたので、
    各 renderGantt* は従来どおり ganttLayout() を読むだけで段ごとの行構成に追従する。
  ・ganttSlotIndexAtY は「段を解決 → その段のローカルY・その段のレイアウトで判定 → 戻り値は全体のタスク
    一覧での index に直す」形にした。段ごとに行を間引くと、その段のレイアウト内の順番＝全体の順番では
    なくなるため、ノード参照から index を引き直す必要がある（ここを数え上げのままにすると挿入位置や
    フェーズ端ドラッグが1行ずれる）。
  ・折り返し時は末尾の空き行を作らない（extra=0）。行間引きで段が短くなったので、空き行が段数ぶん
    積み上がると再び冗長になる。

  ・_gwBands は renderGantt 冒頭で null に戻す。段構成は行・日付・折り返し設定に依存するので、
    状態を変えたら必ず render() を通すこと。

■ なぜ（why）
  ・折り返しONにすると、どのモードでも段の右側の表示が崩れていた（ユーザー指摘「一番右側がすべての

    ① フェーズのロールアップバー（renderGanttPhaseBars）に段のクリップが無く、段の右外まで伸びて

    ② 時間軸ヘッダーの中段の横線が x2=SVG_W のまま＝段より右へ突き抜けていた。
    ③ フェーズ行の帯（時間軸側の色帯）が width=SVG_W-x0 のまま＝キャンバス右端まで伸びていた。

■ 設計判断（why this way）
  ・「描画してよい右端」を ganttRightEdge() に集約した（折り返し中=段の右端＝区間の終わり、通常=SVG_W）。
    折り返しOFFでは SVG_W を返すので従来の描画と完全に同一。右端を各所で個別に計算し直さない。
    はみ出し文字の右詰め（v5.00②のタスクバー/マイルストーン）もこの基準に載せ替えた。
  ・フェーズのロールアップバーはタスクバーと同じ扱いにした（段の帯で切り、はみ出す側は矢羽根）。
    バーの形は「上のスパイン＋左右端が下へ脚」なので、切った側は脚を出さず矢羽根にする
    ＝脚があると「そこでフェーズが終わった」ように読めるため。切らない側の形は従来と同一。
  ・右の空白は「列幅を広げて段を幅いっぱいに使う」で解消した（ganttComputeColW の折り返し分岐）。
    折り返しは横スクロールを無くすためのモードなので、幅を余らせる意味がない。考え方は v5.02 の

    見出し欄OFFのときは元から段=キャンバス幅なので拡大しない。
  ・キャンバス幅・列幅の基準は段の「列数（切り上げ）」ではなく「正味の長さ（小数）」にした
    （ganttWrapMaxBandSpan）。週目盛り＋月ごとは列を切り上げて描き内容は月末でクリップするため、
    切り上げたぶん（最大1列ぶん）がそのまま右の空白になっていた。
  ・依存線（renderGanttEdges）は、両端の行がその段に出ていないときは描かないようにした。

── v8.08 追補③（2026-07-25／同一版内）情報欄の文字が列の枠を越える不具合の修正 ──

■ なぜ（why）
  ・時モードで左情報欄の工程行「工程：2026年8月12日 0時～2026年8月30日 0時」が列の枠を越えていた
    （v8.07 から存在。ユーザー指摘）。真因は ganttClip の文字幅の見積り＝一律 fontPx*0.62。
    全角は fontPx 幅あるので、全角が多い文字列を短く見積もり、切られずにそのまま描かれていた。
    実測で v8.07 は最大 18.8px はみ出し（フェーズ名・工程行の複数箇所）。
  ・折り返しONの調査中に、段をまたぐタスクバーのラベルが「切る前の座標 n.x」に置かれており、
    段の左外＝左情報欄の上に文字が乗るケースを発見（実測 34px 侵入）。段の左端との差が
    1〜2列ぶんのときに起きる（差が大きいと画面外へ出るため気づきにくかった）。

■ 設計判断（why this way）
  ・文字幅の測り方を ganttTextW（全角=fontPx／半角=fontPx*0.55）に集約した。基準は見出し欄の
    mLab と同じ＝アプリ内で二重の見積り方式を持たない。ganttClip もこれで測って1文字ずつ積み、
    「…」の幅を残して切る（従来は文字数で割るだけだった）。
  ・工程行は「切って…にする」より「入るフォントまで落とす」を選んだ（ganttFitFs・下限9px）。
    日付は末尾まで読めないと意味がない情報なので、末尾を落とすより1〜2px縮める方が実用的。
    バー内ラベルの自動縮小（v4.30）と同じ考え方。
  ・段をまたぐバーのラベルは、切ったあとの座標（_bx0／_bx1-_bx0）を基準にした。バー本体だけを
    切ってラベルを元座標に置くと、バーは段内・文字は段外という食い違いになる。
    はみ出し文字の右詰めも、折り返しONでは完了日の指定に関係なく効かせる。
  ・フェーズ名がバーに入らないときの「バーの右に置く」フォールバックは、段の右に余地が無ければ
    バー内に白字で入れる（ganttClip で切る）ようにした。追補②で入れた右詰めだけだと
    バーに重なって読めなくなる（段の幅が限られる折り返しONで起きやすい）。
  ・fits の判定式 label.length*12+12 は据え置いた。ここを正確な幅に直すと折り返しOFFでも
    ラベルの内外判定が変わり、v8.07 との完全一致（回帰チェックの土台）が崩れるため。

■ 検証（how tested）
  ・getBBox の実測で「左情報欄の文字が列境界を越えていないか」を全モードで確認。

── v8.08 追補④（2026-07-25／同一版内）情報欄の無記入の項目の空白を詰める ──

  ・概要（行3）・担当（行4）のどちらも、無記入なら行を作らない。当初は「担当は空でも1行残して
    縦位置を揃える」で実装したが、ユーザー判断で担当も詰める形に変更（2026-07-25）。

  ・詰めた概要セルには当たり判定（addHit）を置かない（高さ0の矩形は押せないので無意味）。

── v8.09（2026-08-03）上書き保存の新設（開いたファイルへそのまま書き戻す） ──

■ なぜ（why）
  ・保存が「ダウンロード」方式（dl＝<a download>）のため、保存先を選べずダウンロードフォルダへ行き、同名が
    あると上書きではなく〜(1).html が増える。過去に何度か仕様を詰めても理想形にならなかったのはこの方式が
    原因で、方式を変えない限り上書きは原理的に不可能だった（ユーザー指摘 2026-08-03）。
  ・ユーザー案は「開いた時のディレクトリを記録し、同名ファイルを上書きする」。ブラウザはページへファイルの
    絶対パスを渡さず、パス文字列を指定して書き込むAPIも無いため、この案そのものは実装できない。

■ 設計判断（why this way）
  ・記録するのは「場所（パス）」ではなく「ファイルへの参照（FileSystemFileHandle）」にした。File System Access API の
    ハンドルは一度ユーザーが選べば以後ダイアログ無しで同じファイルへ書き戻せる＝目的の挙動そのもの。
  ・ハンドルは IndexedDB に保存し、キーは docId（保存データへ埋め込む一意ID）。ファイル名をキーにすると同名の
    別図と衝突するため。docId は buildSaveHtml で未採番なら発行し、状態JSONに載せて保存＝開き直した時に
    自分の保存先を引ける。旧版で保存したファイルは docId が無いので初回だけ保存先を尋ねる（後方互換）。
  ・「名前をつけて保存」は showSaveFilePicker に切り替えた。保存先を選べるようになるうえ、ここで選んだファイルが
    そのまま以後の上書き先になる＝上書き保存の入口を兼ねられる。id:'bdm-save' 指定でブラウザが前回のフォルダを
    覚えるため、実質「前回と同じ場所」が既定で開く。名前入力モーダルは残した（図の名称 S_diagramName を決める
    役割があり、ガント見出しの工事名等に使われるため）。
  ・別ファイルとして保存したときは docId を振り直す。振り直さないと、複製元と複製先が同じIDを持ち、複製先で
    上書きすると複製元を壊す。
  ・記憶していたハンドルを使う前に、中身の docId と（file:// で開いた場合は）ファイル名を照合する。エクスプローラーで
    ファイルを複製すると docId も複製されるため、ID だけでは複製先を開いて上書きした時に複製元を壊しうる。
  ・requestPermission はユーザー操作の直後にしか出せないので、許可の確認をハンドル復元の直後に置き、重い照合
    （ファイルを読んで docId を突き合わせる）は許可を取った後に回した。
  ・Ctrl+S は Ctrl+F と同じく INPUT ガードより前で処理＝入力欄にフォーカスがあっても効く。
  ・生成（buildSaveHtml）と書き出し（ダウンロード／ハンドル書き込み）を分離。非対応ブラウザ・ダイアログ失敗時は
    従来の saveHtmlCore（ダウンロード）へフォールバックするので、既存の動作は失われない。

■ 検証（how tested）
  ・書き込み経路は、ピッカーと同じ FileSystemFileHandle をOPFSから取得して端から端まで実行＝1.4MBの保存HTMLが
    書かれ、docIdを含み、読み直すと状態が完全に復元されることを確認。保存HTMLを iframe で実際に起動させ、
    ノード2件・図種・図の名称・docId・新ボタンまで復元されることも確認した。
  ・「開き直してから上書き」を再現（メモリ上のハンドルを捨てる）→ IndexedDB から復元し、無確認で同じファイルへ
    追記が反映されることを確認。
  ・安全装置＝記憶していた保存先が別の図のファイルだった場合、上書きせず保存先の指定に切り替わり、相手の
    ファイルが無傷であることを確認。
  ・Ctrl+S（キャンバス上／入力欄フォーカス中の両方）で発火、従来のダウンロード保存も正常、コンソールエラー0。

■ 既知の制約
  ・Microsoft Edge / Google Chrome 専用。Firefox・Safari は File System Access API 非対応のため、従来どおり
    ダウンロード保存になる（その旨をヒント表示）。
  ・.html をダブルクリック（file://）で開く運用で最後まで通るかは実機確認が必要。開発環境（Claude内蔵ブラウザ）は
    OSのファイルダイアログを描画しないため、file:// でピッカー呼び出しが拒否されないところまでは確認済みだが、
    実際の選択→書き込みは未確認。通らない場合はダウンロード保存へフォールバックする（壊れはしない）。
  ・同名ファイルを別フォルダへ複製した場合は、docId もファイル名も一致するため区別できない。
  ・セッションの最初の上書き時に、ブラウザの「ファイルの編集を許可しますか」が1回出ることがある（仕様）。

── v8.09 追補（2026-08-04）マインドマップの枝の形を切替式に（曲線／直線） ──

■ なぜ（why）
  ・「枝がたまに意図せず交差する」というユーザー指摘から経路設計を調査した。実測の結果、
    普通に自動整列した図（12ノード）では現行の描き方で交差0・貫通0であり、現行の描き方自体に
    問題は無かった。交差が出るのは、兄弟を手でほぼ同じ方向へ動かしたときに限られる。
  ・原因: 兄弟の枝が親の辺の中央という同じ1点から同じ向きに出るうえ、膨らみが枝の長さに比例する
    （mindBezier の off=max(30,dist*0.4)）ため、長い枝が短い枝を追い越す。加えて出口の辺が
    |dx| と |dy| の大小だけで決まるため、45度をまたぐと right→bottom に突然切り替わる。
    実測: 中心から43度と56度にある2本が、箱が重なっていないのに交差した。

■ 却下した案（why not）
  ・最初に「幹＋放射」案（親ごとに子の平均方向へ合流点を置き、そこから放射する）を提案したが、
    ユーザーから「現行の方が良く見える／改善案は歪」と指摘され取り下げた。
    放射状の図では子が四方に散るため平均方向がほぼ打ち消し合い、合流点が無意味な向きへ飛び出す。
    結果、右にある子への枝が左上から回り込む不自然な形になっていた。片側にだけ子が並ぶツリー表示を
    前提にした設計で、放射状の検証が不足していた。
  ・出口だけを輪郭上にする案・制御点だけ方向沿いにする案も試したが、別条件で交差が増えたため不採用
    （5本の兄弟で交差0→1）。

■ 設計判断（why this way）
  ・両端とも「相手の方向」の輪郭上の点を結ぶ形（＝直線）は、枝が自分の角度の中に収まるため順序が
    保たれ、追い越しが起きない。実測でも上記の交差1件が0件になり、普通の図では交差0・貫通0を維持した。
  ・ただし見た目が直線的に変わるため、置き換えではなく<切替>にした（ユーザー判断 2026-08-04）。
    既定は曲線＝従来のまま。切替はサイドバー「レイアウト」に置いた（配置モードの隣＝図全体の見え方を
    決める設定がまとまる位置）。
  ・輪郭上の点は既存の _edgeBorderToward（手動ウェイポイント経路の端点算出・v4.26）を再利用した。
  ・表示の切替なので snap() は呼ばない。呼ぶと履歴に中身の変わらない段が積まれ、Ctrl+Z が空振りする
    （方眼 toggleGrid・ステップ番号 toggleStepNums と同じ扱いに揃えた）。
  ・属性セグメントの一括制御は '.mind-seg' 全体を対象にしていたため、枝の形セグメントまで
    「ノード未選択なら無効」にされてしまう。セレクタを '.mind-seg[data-key]' に限定して回避した。

■ 検証（how tested）
  ・実クリックで切替が動作し、枝が全て直線（M..L..）／全て曲線（M..C..）に切り替わることを確認。
  ・兄弟を手でほぼ同じ方向へ置いた状態で、曲線=交差1 / 直線=交差0 を実測（描画済みSVGを60分割して判定）。
  ・保存→インポートで枝の形が復元されること、mindBranch を持たない旧ファイルは曲線になることを確認。
  ・切替を3回行っても履歴が増えないこと、属性セグメントの有効/無効・選択表示に回帰がないこと、
    補足情報の細点線と深さ別の太さが直線モードでも保たれること、出力SVGにも直線が載ることを確認。
  ・コンソールエラー0。

■ 残っている課題（未着手）
  ・枝が無関係なノードを突き抜ける（貫通）現象は、描き方をどう変えても直らない。ノードが枝の通り道に
    置かれているため。以下の配置側の改修が必要:
    ①Tabの子追加位置が「親の右へ70px」固定で、親が中心より左だと中心へ戻る（実測で貫通2件）。
     中心から外向きに置けば0件になることは確認済み。
    ②放射状レイアウトが角度を葉の数だけで配り半径を深さ×185px固定にしているため、箱の幅ぶんの
     角度が確保されていない。
    ③ツリーの兄弟の並び順がエッジ追加順で、ドラッグで並べ替えても整列すると元に戻る
     （樹状図 orgTreeLayout は現在位置順にソート済み＝同じ考え方を持ち込める）。

── v8.09 追補②（2026-08-04）マインドマップの配置改修（枝の貫通の解消） ──

■ なぜ（why）
  ・枝が無関係なノードの箱を突き抜ける（貫通）現象は、枝の引き方をどう変えても直らない。
    ノードが枝の通り道に置かれているため＝配置側の問題であることを実測で切り分けた（追補①参照）。
  ・原因は3つ。(a) Tabの子追加が『親の右へ70px』固定で、親が中心より左にあると新しい子が中心方向へ
    戻り既存の枝の下へ潜り込む（実測 貫通2件）。(b) 放射状レイアウトが角度を葉の数だけで配り半径を
    深さ×185px に固定していたため、箱の幅ぶんの角度が確保されない。(c) ツリーが列210px・行54px固定で、
    文字数の多い箱や重要度『高』の箱がはみ出す。

■ 設計判断（why this way）
  ・(a) 中心→親の方向の延長150pxへ置き、兄弟は外向きと直交する向きへ左右交互に振り分ける
    （0, +52, -52, +104 …）。一方向へ積むと群れが片側へ寄るため交互にした。親が中心トピックのときは
    既存の枝の角度を見て一番空いている隙間の中央へ伸ばす。
  ・(b) サブツリーの重みを『葉の数』から『必要な弧の長さ（葉の箱幅＋余白の合計）』に変更し、
    深さごとの半径を max(前の深さ+185, その深さの必要弧の総和÷2π) にした。混み合う階層だけ外へ広がる。
    サブツリーが互いに素な扇形に入る従来の構造はそのまま活かしている。
  ・(c) 列xは各深さの最大幅から積み上げ、行は実際の n.h ＋一定の隙間で詰める（樹状図 orgTreeLayout と
    同じ考え方）。

■ やり直した点（重要）
  ・当初は orgTreeLayout に倣い『整列のたびに兄弟の並び順を現在位置から決め直す』実装にしたが、
    配置モードを切り替えただけで順序が入れ替わる不具合になった。放射状で円周に散った子を
    ツリーのY順で並べ直すため、アウトラインから作った直後の図が『甲乙丙丁』→『丁丙甲乙』になる。
  ・そこで『ドラッグで動かした時点で一度だけエッジの並びへ確定する』方式に変更した
    （mindReorderSiblings をドロップ完了時に呼ぶ）。整列はエッジ順に従うだけなので、
    アウトライン順は保たれ、並べ替えた結果はどのモードで整列しても維持される。
    並び順の基準は、ツリー＝Y座標、放射状＝親まわりの角度（内向きを起点に一周）。

■ 検証（how tested）
  ・描画済みSVGパスを60分割して交差・貫通・箱の重なりを数え、次の全ケースで 0/0/0 を確認:
    普通の図(12ノード)／第1階層10本／長いラベル6本／3階層(17ノード)／ツリー3階層／ツリー長いラベル／
    Tabで左側の枝に2つ追加（改修前は貫通2）／手で動かした図を整列（改修前は整列しても貫通2）／直線モード。
  ・並び順: アウトライン順が生成直後もモード切替後も保たれること、ドラッグで先頭へ動かした順序が
    再整列・モード切替をまたいで維持されること、その Undo/Redo が効くことを確認。
  ・Tab追加のUndo、Enterの兄弟追加、折りたたみ中の整列、中心トピック1つだけの図、保存→復元、
    樹状図(orgTreeLayout)への影響なし、コンソールエラー0 を確認。

■ 既知の範囲
  ・手でノードを枝の通り道へ置いた直後は貫通が残る（利用者が置いた位置のため）。「整列を実行」で解消する。
  ・保存済みファイルはノード座標をそのまま復元するので、開いただけでは配置は変わらない
    （整列を実行したときに新しい間隔になる）。


── v8.10（2026-08-05）シェイプ編集まわりの改良（8点） ──

■ 背景（なぜやったか）
  ・通常シェイプには自動リサイズが一切なく（editText の確定は n.text を入れるだけ）、長い文章を入れると
    文字が枠外へ流れて隣のシェイプと重なる。折り返しも Alt+Enter の明示改行だけで、幅に応じた自動折り返しが
    無かった（wrapText はガントの説明欄と note の備考欄でしか使われていなかった）。
  ・画面移動の手段がスクロールバーだけ。パレットでシェイプを選んだままキャンバスをドラッグすると配置になる。
  ・マインドマップの枝色は「その枝が S.edges の何番目か」で決まるため、枝をドラッグすると
    mindReorderSiblings がエッジ順を書き換え、色が総入れ替えになる。並び順と色が同じ根拠を共有していた。
  ・放射状整列は常に角度0（真右）から配り直すため、整列のたびに図全体が回る。
  ・レーン見出しは g-lanes の中に y=0 固定で直描きされており、縦スクロールで一緒に流れて消える。
  ・文字編集中に余白をクリックすると、svgMD が blur(=確定) より先に走るため、確定と配置が同時に起きる。

■ 設計判断（why this way）
  ・自動リサイズは render() の1か所（note の自動リサイズの直後）で全ノードに掛ける。編集確定・置換・
    インポート・テキスト作図など、どの経路で本文が変わっても自動的に効く。マインドマップが
    calcMindNodeSize を renderMindmap 冒頭で回しているのと同じ考え方。
  ・折り返し後は「実際に一番長くなった行」に合わせて幅を詰め直す。上限幅のまま置くと、短い行が並んだときに
    左右が間延びして見える（モック提示時にユーザーから指摘）。文字の左右余白は片側5px。
  ・縦書き（横モード）は wrapText を使わず文字数で列を切る（wrapTextByCount）。縦書きは半角も全角も
    同じ送りで積むため、幅で折り返すと半角混じりの行で送りがずれて箱からはみ出す。
  ・入力中の追従は openSvgEditor に opts.onInput を足して実現。エディタは SVG 直下にあり render() の
    g-nodes 差し替えでは消えないため、毎キー render() してもフォーカスは保たれる（v7.05 の配置が効いた）。
    履歴は確定時の1回だけ積む（入力中に snap() すると1文字ごとに履歴が積まれる）。
  ・ハンドツールは #canvas-wrap のキャプチャフェーズで mousedown/click/dblclick を握りつぶす方式にした。
    SVG やノード <g> のハンドラより先に走るので、配置・選択・接続・ダブルクリック編集を個別にガードして
    回らなくて済む。S.mode は保存対象に入っていないため保存フォーマットへの影響もない。
  ・枝色はノードの optional プロパティ branchIdx へ焼き付ける。未設定なら従来どおりエッジ順で決めるので、
    旧ファイルは開いた瞬間の色がそのまま固定される（mindAssignBranchIdx が「その時点のエッジ順」を採る）。
    S.nodes ごと保存・Undo に乗るので、保存フォーマットの追加作業は不要。
  ・整列の方角維持は「並び順は変えず、扇全体の回転だけを現状へ寄せる」方式。各枝に割り当たる新しい角度と
    現在の角度の差を円周平均（atan2(Σsin, Σcos)）で求めて起点角に足す。角度の巻き（±π境界）に強く、
    1回の計算で済む。並び順まで位置から決め直すと v8.09 で直した不具合が戻る。
  ・レーン見出しは g-lane-hdr（最前面）へ分離し、スクロール量÷zoomLevel だけ平行移動する。
    レーン並べ替えが見る軸は縦モード=X・横モード=Y で、動かす軸と直交するため座標補正は要らない。
    出力（buildExportSvg）と保存（buildSaveHtml）では transform を外してから書き出す。
  ・編集中の余白クリックは、closeSvgEditor() で blur を明示的に呼んで確定させてから return する。
    このとき選択も外す。残したままだと v8.05 の「選択中の余白クリックは選択解除だけ」に引っかかり、
    置きたいときに3クリック必要になる（マインドマップは選択＝次の配置の親なので残す）。

■ 検証（how tested）
  ・入力中: 1文字ごとに箱と編集欄が育ち、260pxで頭打ち→折り返して縦へ伸びること。文字を消すと既定へ戻ること。
    手動リサイズ後は幅が変わらず高さだけ追従すること。横モード（縦書き）で列送りになり箱に収まること。
  ・履歴: 5回入力しても hist は増えず、確定で1回だけ増える。Undo 1回で入力前の本文へ戻る。
  ・ハンドツール: パレット選択が外れる／ドラッグ量ぶん正確にスクロールする（200→320px）／
    ノードが増えず選択も付かない／ダブルクリックで編集にならない／Esc と「選択」で復帰する。
  ・マインドマップ: 枝を動かして整列しても A=青 B=緑 C=橙 D=赤 が不変。整列を3回繰り返しても角度が動かない
    （＝図が回らない）。v8.09 で保存した状態を読み込んでも色が変わらない。文字が箱に収まる（getBBox で実測）。
  ・レーン見出し: 520pxスクロールで transform=translate(0,520)、ズーム150%で 1/1.5 に補正される。
    スクロール中の見出しドラッグでレーン並べ替えが正しく効く。出力SVG・保存HTMLに transform が残らない。
  ・回帰: 10図種すべてでパレット全種の配置・render・buildExportSvg・buildSaveHtml がエラー0。
    ガントの gantt_summary の w/h が undefined なのは v8.09 と同一（既存挙動）。

■ 既知の範囲
  ・自動リサイズの対象外: note/state_detail（従来の備考リサイズが担当）、区画を持つシェイプ（ER/UML/樹状図）、
    グループ枠、ラベルが枠外の event/gateway、ステップ図の列に属するシェイプ、ガント・シーケンス・
    マインドマップ専用シェイプ（マインドマップは calcMindNodeSize が担当）。
  ・方角維持は「概ね」。兄弟を2本ほぼ同じ角度へ寄せた状態で整列すると、均等に配る過程でどちらかが大きく動く。
  ・レーン見出しの固定はスイムレーン／BPMN のみ。ガントの見出し・時間軸ヘッダーは同じ問題を持つが対象外。


── v8.10 追補（2026-08-05）ハンドツールの操作範囲拡張・検索パネル・メニューバー開閉・文字揃えの全面適用 ──

■ 背景（なぜやったか）
  ・v8.10 のハンドツールは #canvas-wrap のキャプチャフェーズで mousedown/click/dblclick を
    無条件に握りつぶす「パン専用」だった。手っ取り早く配置・選択・接続をまとめて止められた反面、
    画面を動かしながら箱を1つ直したいだけでも、いちいち「▶ 選択」へ戻す必要があった。
  ・検索パネルの閉じるボタン（✕）は検索欄と同じ行の右端にあったが、その行が幅300pxのパネルに
    収まっておらず、✕ の実際のx座標がパネルの右端より外（1392 > 1382）にあった＝画面上で切れて
    見えなかった。「閉じるボタンがない」というのはこれ。あわせて位置も固定で、探している最中に
    図の右上が隠れても避けられなかった。
  ・ツールバーは図種によっては3段に折り返し、縦方向を100px以上使う。図を広く見たいときに畳めない。
  ・文字揃え（textAlign）は D-5 v4.28 で入れたが、反映されるのは「横書きの汎用シェイプ本文」と
    「付箋のタイトル（縦モード）」だけだった。マインドマップ・樹状図・UML・ER・グループ枠・
    ライフライン・BPMNのイベント/ゲートウェイ・ガントのバーはどれも中央または左に固定で描いており、
    ボタンを押しても何も起きない（＝ユーザー報告のとおり）。

■ 設計判断（why this way）
  ・ハンドツールは「握りつぶす対象から外す例外」を1か所（handPassThrough）に集約した。
    通すのは <g data-nid>（シェイプ本体）と #svg-editor（文字編集欄）の中だけ。ハンドツール中に
    してよいのは移動とダブルクリック編集までで、それより先の操作（リサイズ・接続・右クリック削除）は
    通さない。リサイズハンドルは選択モードでしか描かないので自然に外れる（crosslane の幅調整ハンドルは
    S.mode!=='connect' で描いていたので S.mode==='select' へ狭めた）。contextmenu は種類を問わず
    握りつぶす＝ハンドツール中に右クリックで消えると事故になるため。
  ・ガントのバー/マイルストーンの <g> には data-nid が無く、ハンドツールの例外判定から漏れていたので
    attachGanttNodeHandlers で付ける。汎用ノード・マインドマップと同じ目印に揃えた。
  ・ハンドツール中に余白を押したときは closeSvgEditor() で確定だけ行って return する（画面は動かさない）。
    選択モードの v8.10⑦ と同じ挙動。ここを通さないと、ハンドツール中は編集を確定する手段が
    Enter/Esc だけになる。
  ・検索パネルは行の詰まりを直すのではなく、掴める見出し帯を新設して ✕ をそこへ移した。
    行に5つ（入力・件数・▲・▼・✕）を並べる設計自体に無理があり、✕ を最初に押し出していた。
    行のはみ出し自体も input{min-width:0} で解消（flex アイテムは既定で内容幅より縮まない）。
    .tbtn は暗いツールバー用の淡色なので、白いパネルの上では #search-body 内だけ濃くする。
  ・パネルの初期位置は right 指定なので、掴んだ時点で left/top 指定へ切り替えてから動かす。
    置いた位置は開き直しても保つ（探しながら見たい場所へ寄せられるようにするため）。
  ・「メニューを隠す」ボタンは絶対配置でツールバーの右下角に固定し、ツールバー側に
    padding-right:128px を入れて場所を空ける。通常のフレックス要素として最後に置くと、
    折り返したときにボタンだけが次の行の左端へ回り、「一番右下」にならない（実測で確認）。
  ・隠す対象はツールバー（#toolbar）だけで、図種ラベルのある見出し（#app-title-bar）は残す。
    図種の切替はそこからしか行えないため。再表示ボタンは画面右下に常駐させ、隠している間だけ出す。
  ・文字揃えは alignH（横書き＝枠内の左/中央/右）と alignVCy（縦書き＝行が上から下へ流れるので
    左揃え＝上・右揃え＝下）の2つのヘルパへ集約し、各描画から呼ぶ。縦書きに「左右」は無いが、
    横書きを90度倒したときに対応するのは上下なので、同じボタンで扱う（行頭揃え／行末揃え）。
  ・既定（textAlign 未設定）の見た目は変えない。UMLの属性・操作行とグループ枠のタイトル帯は
    既定が左詰めなので、揃えを明示したときだけ従う分岐にした。
  ・対象外にしたもの: ミニ表のセル（列としての揃えが優先）、ステップ番号サークルのラベル
    （円の右／下という位置自体が意味を持つ）、ガントのマイルストーン名とフェーズ名
    （◆は幅20pxで寄せる余地がなく、フェーズ名は左のブラケット列の構造物）、
    バーに収まらず上へ出したラベル（左端に合わせないと隣のバーの文字と重なる）。

■ 検証（how tested）
  ・ハンドツール（Chromium 実操作）: シェイプのドラッグで移動する／余白のドラッグでスクロールする／
    余白クリックで配置されない／シェイプのダブルクリックで編集欄が開く／編集中に余白を押すと
    確定だけ起きる、の5点を自動テストで確認。
  ・文字揃え: 10図種 × 縦横2方向 × パレット全種（90通り）を総当たりし、left/center/right で
    実際に <text> の描画位置が3通りに分かれるかを getBBox で実測。82/90 が変化する。
    残り8件の内訳は、置き方が特殊で自動配置できなかった2種（BPMNイベント・活性区間）＝別途
    addNode 経由で3通りに分かれることを確認、文字を持たない2件、意図的な対象外4件（マイルストーン・
    フェーズ）。
  ・回帰: 同じ90通りについて textAlign 未設定のまま追補前後の <text> 位置を突き合わせ、
    差分は「ガントの <g> に data-nid が付いた」ことによる4件のみ（描画位置の変化なし）。
  ・検索パネル: 見出しのドラッグで移動する／画面外へ出ない／✕ で閉じる。行の全要素がパネル内に
    収まること（▼ の右端 1373 < パネル右端 1382）を実測。
  ・メニューバー: 隠す→ツールバーが display:none、右下（1386,886）に再表示ボタン→戻る。

■ 既知の範囲
  ・自動リサイズで箱が文字に張り付く種類（マインドマップ・折り返し対象の汎用シェイプ）は、
    1行だけの本文だと箱に余白が無いので揃えても見た目が変わらない。複数行にするか手で広げると効く。
  ・縦書き（横モード）で列が箱の高さいっぱいになる場合も同様に、その列は動かない。
  ・ハンドツール中もキーボード操作（Delete・Ctrl+C/V など）は選択モードと同じに効く。

■ 版の扱い（なぜ v8.11 ではなく v8.10 の追補にしたか）
  ・この一式は当初 diagram_v8.11.html として版を上げ、main へ直接 push していた。
    しかし中身は「効かなかった／切れていた／触れなかった」の手当てが主で、運用ルールの
    「バグ修正のみのセッションは版を上げない（最新版を直接更新して追補として記録する）」に当たる。
  ・そこで diagram_v8.11.html を diagram_v8.10.html へ戻し（ファイル内の版表記・コメントの
    "v8.11" も v8.10 へ統一）、99_旧バージョン/ へ退避していた追補前の v8.10 は削除した
    ＝追補は新ファイルを作らず最新版を直接更新する運用のため。
  ・履歴は書き換えず、打ち消しコミットで戻す（v8.11 のコミットは残るが main は force push しない）。
  ・副作用として serve.js の配信先（diagram_v8.10.html）が再び最新版と一致した。
    v8.11 のとき更新漏れがあり、ルート最新版とプレビュー配信先がずれていた。

── v8.11（2026-08-06）ガントの見出し欄・時間軸ヘッダー・タスク名列を固定 ──

■ 背景（なぜやったか）
  ・v8.10 でスイムレーン／BPMN のレーン見出しを固定したとき、「ガントの見出し・時間軸ヘッダーは
    同じ問題を持つが対象外」と既知の範囲に残していた。今回そこへ着手した。
  ・ガントは横に長い（既定のサンプルでキャンバス幅 2276px に対し表示幅は 1000px 前後）。
    下や右へスクロールすると、どの工程の行なのか・いつの日付なのかを示すものが画面から消える。

■ 方式（なぜこの作り方か）
  ・表計算のウィンドウ枠固定と同じ考え方で3つに分けた。
      上（g-gantt-top）  = 見出し欄＋時間軸ヘッダー … 縦スクロールだけ追従
      左（g-gantt-left） = タスク名列＋フェーズ列   … 横スクロールだけ追従
      角（g-gantt-corner）= 左上コーナー            … 縦横どちらも追従
    描画順は 左→上→角。重なったときに角が最前面へ来る＝列の見出しが常に列の上に残る。
  ・当初は v8.10 のレーン見出しと同じく「専用レイヤへ描いてスクロール量ぶん平行移動する」方式に
    したが、スクロール中に揺れたため下の「追補」のとおり position:sticky へ差し替えた。
    どちらの方式でも、図の座標（n.x/n.y・行スロット・日付→X）は一切動かさない。だから保存・PDF・
    画像・Excel、折り返し計算、当たり判定の既存コードに手を入れずに済んでいる。
  ・見出し欄は縦だけ固定で、横は流す。キャンバス幅いっぱい（SVG_W）に広がるため両方向で固定すると
    画面より右にある承認欄・凡例へ永久に届かなくなる。縦に固定してあれば工事名は常に見える。
  ・折り返し表示中（wrap）は対象外。段ごとに時間軸ヘッダーを持つので上に貼り付けると別の段の
    日付を指してしまうし、折り返しは横スクロールを無くすための機能なので左固定も要らない。

■ つまずいた点と対策
  ・固定レイヤは見た目だけをずらすので、固定した帯の下には本体の行やバーが潜り込む。
    左上コーナーの背景は pointer-events:none だったため、コーナーをクリックすると下の工程行の
    当たり判定に抜けていた（elementFromPoint で確認）。各レイヤの最下部に透明のシールド矩形
    （ganttStickyShield）を敷いて解決。シールドは自前のハンドラを持たずイベントを canvas 側へ
    通す＝「情報欄をクリックして工程を追加」（v5.00 ③）は従来どおり効く。
  ・そのうえで、掴んだ位置を「そこに見えているもの」の座標へ読み替える（ganttStickyPt）。
    これが無いと、横スクロール後にタスク名列を掴んでも px が leftW を超えているため
    「時間軸の上」と判定され、情報欄ではなく日付から工程が置かれてしまう。
  ・行ドラッグ（ganttSlotIndexAtY）は縦位置だけ、列幅ドラッグ（mode:'colw'）は横の移動量だけを
    見るので、平行移動しても補正は要らない。動かす軸と判定に使う軸が直交しているため。
  ・図種を切り替えたときに固定レイヤが残り、スイムレーンの上へ前のガントの見出しが浮いたままに
    なった。汎用の描画パスは各レンダラが自分のレイヤだけを空にする作りで、共通のクリアが無い。
    render() の先頭で3レイヤを空にして transform も外すようにした。

■ 確認したこと
  ・スクロール 600/300 で transform が left=translate(600,0) / top=translate(0,300) /
    corner=translate(600,300) になり、画面上の位置が 左=x0・上=y0・角=x0かつ時間軸の帯に載る。
  ・当たり判定: 角→角レイヤ、時間軸の帯→上レイヤ、見出し欄→上レイヤ、タスク名列（行・空き）→
    左レイヤ、本体→従来どおり。横スクロール後に情報欄クリックで工程が1件増える／固定ヘッダーの
    クリックでは増えないことを実行して確認。
  ・書き出し（buildExportSvg）と保存HTML（buildSaveHtml）に transform が入らず、レイヤの中身
    （78/27/1要素）は残ること。保存後に画面側の固定が戻ること。
  ・折り返しON＝固定しない（レイヤ空・従来の g-dividers へ描画）、OFFで復帰。
  ・9図種を順に描き直してコンソールエラー0、固定レイヤの残留なし。
  ・画面のスクリーンショットは、この環境ではブラウザペインが非表示で取得できなかったため、
    位置・当たり判定は getBoundingClientRect と elementFromPoint の実測で確認した。

■ 既知の範囲
  ・折り返し表示中は固定しない（上記のとおり）。
  ・見出し欄は横スクロールで流れる（承認欄・凡例へ届くようにするため意図的）。
  ・ガントの拡大縮小は列幅で行い zoomLevel は常に1だが、追従量は他図種と同じく zoomLevel で
    割ってSVG座標へ直している（将来ズームを入れてもそのまま動く）。
■ 追補（2026-08-06）JSでの追従をやめ position:sticky へ
  ・症状: スクロール中、固定したはずの見出し・時間軸・タスク名列がわずかに揺れる（ユーザー指摘）。
  ・原因: スクロールの描画はコンポジタ側で先に進み、scroll イベントで当てる transform は
    そのあと＝1フレーム遅れて追いつく。JS で追従させるかぎり原理的に消せない。
  ・対策: 位置合わせをブラウザに任せる。本体SVGの前に幅0・高さ0の箱（.gstick）を置き、その中の
    SVGを絶対配置で重ねて、そこへ3レイヤを描く。固定したい軸だけ top / left を指定する＝
    上は top:0（縦だけ固定・横は流れる）、左は left:0、角は両方。スクロール中に走る JS は無い。
  ・箱を本体SVGの外へ出したのは position:sticky が SVG の中身には効かないため。幅0・高さ0＋中の
    SVGは絶対配置なので、スクロール範囲（scrollWidth/Height）には影響しない。
  ・当たり判定は変わらない。svgPt は本体SVGの行列で換算するので、重ね箱の中の要素を掴んでも
    返るのは「その画面位置に対応する本体の座標」＝これまでどおり ganttStickyPt で読み替えられる。
    重ね箱のSVGにも svgMD / svgDbl / svgRC を付けて、本体と同じ操作が届くようにしてある
    （SVGのルートは pointer-events:none、中のレイヤだけ auto ＝空き部分で下を塞がない）。
  ・書き出しは要注意だった。buildExportSvg は #diagram-svg を clone するので、外へ出した3レイヤが
    そのままでは PDF・画像から丸ごと落ちる。clone のあとに3レイヤを append して取り込む。
    座標系は本体と同じなので、スクロールしたまま書き出しても図の本来の位置で出る（確認済み）。
  ・確認: スクロール 0/600・300/1100・400 で、左レイヤの画面x=0固定・上レイヤの画面y=0固定・
    角レイヤのx,y固定を getBoundingClientRect で実測。当たり判定と情報欄クリックの工程追加、
    書き出しへの取り込み、9図種の切替、折り返しON/OFF、他図種でのズームも再確認しコンソールエラー0。
  ・同じ揺れを持っていたレーン見出し（v8.10・スイムレーン／BPMN ほかレーンを使う図種）も、
    続けて同じ作りへ寄せた（ユーザー要望）。重ね箱は #gstick-lane の1つで、止める軸は向きで
    変わる＝縦モードは top:0（上端）・横モードは left:0（左端）なので、そこだけ syncLaneSticky が
    JS で切り替える。ガントの3箱とは同時に有効にならないため重なり順の競合は無い（レーン=4、
    ガント=5/6/7）。stickyLaneHeader と initStickyHeader（scroll リスナ）は削除。
    レーン見出しは帯の全面がドラッグ用の矩形で埋まっているので、ガントのような透明の板は要らない。
    レーン並べ替えは交差軸（縦モード=X・横モード=Y）だけを見るため、止める軸と直交していて
    座標補正も要らない＝スクロールしたまま掴んでも従来どおり動く（実際に並べ替えて確認）。
    書き出しは g-lane-hdr も本体SVGの外へ出たので、ガントの3レイヤと同じく取り込む。

■ なぜ

    いないことに気づけなかった。
  ・議論中に出た「今どこに置くべきか分からない話」を脇に置く場所が無い。思いついた時点で図に

■ 未保存判定に「指紋方式」を選んだ理由
  ・S.hi（履歴位置）の監視では取りこぼす。snap() が積むのは lanes/nodes/edges/gantt/mindLayout
    の5キーだけで、方眼のオン・オフ／ステップ番号／デザインテンプレート／図の名称／レーン名／
    ガント行名／枝の形／ガント見出しの開閉は snap() を通らない。
  ・そこで「保存する内容そのもの」を JSON.stringify し、最後に保存した時点の文字列と比べる。
    元に戻せば必ず一致するので、誤検知が原理的に起きない。
  ・uid は指紋から外した。restore() が巻き戻さない単調増加カウンタなので、シェイプを1つ足して
    Ctrl+Z すると見た目は元通りでも uid だけ進み、永久に「未保存」のままになってしまう。
  ・docId も外した。保存先を照合するための内部IDで、openImportFile や buildSaveHtml が遅延生成
    するため、含めるとファイルを開いた直後にいきなり未保存扱いになる。
  ・判定は例外が出たら false にする。判定できないことを理由にタブを閉じられなくしないため。
  ・コストは閉じる瞬間の1回だけ。snap() は同程度の量をユーザー操作のたびに stringify して履歴を
    80件保持しているので、無視できる。

■ ダウンロード保存も「保存済み」とみなす割り切り
  ・saveHtmlCore（ダウンロード保存）は完了を検知できないが、ここで基準を更新しないと
    Firefox/Safari では保存しても毎回警告が出て、警告そのものが形骸化する。更新する側を採った。

■ タブを閉じるときに4択を出せない理由 → 2段構えにした
  ・beforeunload に出るダイアログは文言もボタンもブラウザが決める固定文（離れる／キャンセル）で、
    そこに「上書き保存」を差し込む API は存在しない。閉じられないページを作れてしまうため意図的に
    塞がれている。
  ・そこで、アプリ内の破棄操作（図種切替・新規作成・ファイル読み込み）＝こちらが主導権を持つ場面に
    4択（上書き保存／名前を付けて保存／保存しない／キャンセル）を置いた。どれも起こりうるので
    どれも1クリックで選べるよう縦に並べる（横1列だと430px幅に収まらない）。
  ・タブを閉じる側は、beforeunload の中で setTimeout を張る。離れた場合はページごと消えてタイマーは
    発火せず、キャンセルして残った場合だけ発火する＝その直後にこちらの選択肢を出せる。この時点では
    閉じる操作がもう取り消されているので「保存しない」に当たる動作が存在せず、3択にしてある。
  ・保存を選んだときは保存が成立したときだけ次へ進む。失敗したのに図が消えると取り返しがつかない
    ため、失敗・中止ならダイアログは開いたまま（原因は赤トーストに出る）。成否は savedFingerprint
    ではなく savedSeq（保存成立の回数）で見る＝同じ内容を2回保存すると指紋が変わらないため。
  ・図種切替の確認条件に isDirty() を足した。従来は「シェイプが1つも無ければ即切替」だったが、
    レーン名や図の名称だけ変えた状態も失われるため。

■ トーストを保存HTMLへ焼き込まない
  ・buildSaveHtml は document.documentElement.outerHTML を丸ごと文字列化する。トースト表示中に
    保存すると class="show" と文言がファイルに焼き込まれ、そのファイルを開くと中央に消えない
    トーストが出たままになる。#svg-editor の削除と同じ場所で toastHide() を呼んで防いだ。
  ・#hint は100箇所以上から呼ばれる常設のステータス行なので置き換えず併設した。
    役割分担は「中央トースト＝保存の結果」「#hint＝従来どおり下段の詳細」。

■ リザーブ領域の作り
  ・一覧の各行は「形プレビュー付きのカード」ではなく、配置後と同じシェイプそのものを描いている。
    置いたら何が出るかが見たまま分かるのと、1件あたりの高さを34pxに抑えられるため（当初案の
    2段組みカードは約70pxで、1つのトピックが画面を占領しすぎた）。
  ・入力欄は一覧の上。書いた直後の項目がすぐ下に積み上がる並びになる（ユーザー指定）。
  ・分類ボタンはシェイプの右に3つ縦積み（26x13px）。絵柄も凡例と同じ3つの形にしてあるので、
    押すと左のシェイプがその形に変わることが見て分かる。文字ラベルは入れていない。
  ・一覧は render() のたびに作り直すので、ganttPanel と同じ再構築ガード
    （if(activeElement が一覧の中) return）を入れた。入れないと編集中に DOM ごと消える。
  ・ドラッグは HTML5 の D&D ではなくマウスイベント方式（palDragStart と同じ作法）。座標換算は
    #diagram-svg に transform:scale() が掛かっているため svgPt ではなく
    getBoundingClientRect()+/zoomLevel を使う。
  ・ドロップは placeShape を通さない専用経路にした。placeShape の冒頭には v8.09 の
    replaceTargetAt（重ね置きで形状だけ入れ替え）があり、そこを通すと入力した文章が失われる。
    既存トピックの上に落としたらその子にし、親の右隣に置く（親の上に重ねない）。
  ・undo 対象に含めた（追加・分類変更・削除・配置は「編集」なので元に戻せるべき）。図を作り直す
    経路（図種切替・テキスト/CSV/Mermaid 取込）ではリザーブもクリアする＝前の図の話が残らない。

■ 確認
  ・snap() が拾えていなかった各キー（方眼／ステップ番号／テンプレート／枝の形／向き／図の名称／
    レーン名／リザーブ）で「変更→未保存、元に戻す→保存済み」を実測。addLane→undo で uid だけ
    進んでも未保存にならないこと、docId を書き換えても未保存にならないことも確認。
  ・beforeunload は合成イベントの defaultPrevented で clean=false / dirty=true。保存HTMLに
    トーストが焼き込まれないこと、保存キーが15個（従来14＋mindReserve）で並び順が保たれること。
  ・4択は「キャンセル＝切り替わらない」「保存しない＝切り替わる」、保存失敗時はダイアログが
    開いたままで次へ進まないことをスタブで確認。
  ・リザーブは 登録／分類（形が凡例どおり rect・polygon・path に変わる）／ダブルクリック編集
    （途中で render() が走っても入力欄が消えない）／ドロップ（空き場所=中心の子・既存の上=その子・
    ドロップ先の type と text が不変・一覧から消える）／undo・redo／保存と読み込みの往復／
    mindReserve が無い旧ファイルで [] になり未保存にならないこと、を実測。

■ v8.13（スイムレーン等レーン図の印刷範囲を内容に最適化）

  ─ なぜ直したか（症状 → 原因）──────────────────────────────────────────────
  ①「交差してもブリッジ（半円）が出ない／交差が何か所あっても1か所しか出ない」
     原因は2つ重なっていた。(a) renderEdges のパス2が「戻り線 × 順方向線」の一方向しか見ておらず、
     順方向どうし・戻り方向どうしの交差には山が一切出なかった。(b) 交差ありの戻り線は経路"全体"を
     白い太線(5px)で先に描いて下を消していたため、交差していない場所でもレーン色・境界線・並走する
     だけの線が白く削れ、検出できなかった交差は「ただ途切れた線」に見えていた。
     「手で経路を編集すると直る」の正体もここ。手動支点(waypoints)を打つと wps が null になって
     ブリッジ機構から完全に外れる＝白い縁取りごと消えるので、途切れて見える現象だけが解消していた。
     区間スライド(orthoWps)の場合は座標が整数へ丸められて交差位置が角やマージンから外れ、
     たまたま検出に成功していた。
     対策＝(a) 全ペア総当たりにし、ペアごとに「戻り線が跨ぐ／同種なら S.edges で後にある線が跨ぐ」で
     必ず一方だけを跨ぐ側に決める（決定的）。端点のシェイプを共有するペアは除外＝ポート付近で接するのを
     交差と誤認しない。手動支点の曲線とバス経路は対象外（曲線は smoothPath の三次ベジエで折れ線とずれる／
     バスは意図的に重なる別の体系）。(b) 経路全体の白は廃止し、renderEdges 末尾の第3パスで
     「山ごとに 白5px → 本体色」を最前面に描き直す。跨がれる側は半円と交わる位置だけが途切れ、
     交差していない場所は切れない（ユーザー確認済みの見え方）。
     判定側も作り直した。旧 findCrossings は端部マージンが2pxしかなく、曲がり角の手前の交差でも
     半径12の半円が角を突き抜けて経路が壊れた／重複除去が無く同一座標に重なった線があると同じ点へ
     半円が二重挿入されて経路が12px後戻りした／24px未満に近接した交差で挿入点が逆順になった／
     判定は折れ線・実描画は角丸(18)なのに wpPathBridge の既定が20で不一致だった。
     対策＝収集(bridgeCollect)と正規化(bridgeNormalize)の2段にし、同一点の除去・近接交差のひと山への統合・
     「その角で実際に使われる角丸半径」を端部マージンにする（bridgeCornerR は wpPath と同じ式）。
     収まらない山は立てない＝山は必ず直線部にしか立たないので、折れ線判定と角丸描画が構造的に一致する。
     半径は 18 に統一。横の線も上へ膨らませる（縦は右）＝定番の飛び越え記法にそろえた。

  ②「別レーンへつなぐと、90°に1回曲げれば済むのに2回曲がる」
     allocatePorts は出口を facingSide で決めたうえ、v8.02 の追補が「相手が主軸方向に完全に離れていれば
     入口を主軸の辺へ強制」していた。出口も入口も主軸の辺になると、交差軸方向にずれている別レーンの
     相手へは直交経路が必ず2回曲がる（Z字）。
     参考PDF（参考資料/購買申請業務 As-Is）の形は「主軸の辺から出て、相手の横辺へ入る」＝1回曲げで、
     現行はちょうど入口と出口が逆だった。対策＝交差軸で箱どうしが L_MIN_GAP(24px) 以上離れていて、
     かつL字の2本が他の箱を貫通しない（lShapeClear が既存の routeObs/vHit/hHit で確認）ときだけ
     「出口＝主軸の辺／入口＝源のある側の横辺」にする。貫通する場合と、交差軸で重なっている
     （ほぼ真下・真上）場合は従来どおり主軸の辺から入れる＝v8.02 の狙い（遠い相手が横辺から入って
     途中の箱を貫通するのを防ぐ）は維持。主軸方向に重なっている相手はそもそも分岐に入らないので、
     参考PDFの「見積依頼→見積書作成」「決裁書・注文書回覧→承認」は従来どおりまっすぐ横へ引かれる。

  ③「①の形にすると、そこから水平の相手へ出る線と重なる」（ユーザー指摘・参考PDF②の見積受領）
     同じシェイプの同じ辺に2つの端が集まる。1st pass の扇状分散は 1/3・2/3 に分けるが、そのあと
     processFan の直交群分岐が入口を setS(...,0.5)＝辺の中央へ上書きし、相手へ向かう線は「一直線優先」で
     中央付近に居座るため、2本がほぼ同じ高さに並んで横向きの区間が長く重なっていた。
     対策＝接続点は「等間隔・最小10px（PORT_MIN_GAP）」でそろえる。
     (a) render() の autoFitNodeSize 直後に growForPorts を走らせ、同じ辺に n 本が集まる箱で
     等間隔の間隔（辺の長さ÷(n+1)）が 10px を割るなら、箱のほうを 10*(n+1) まで広げる
     （setSizeKeepCenter なので中心は動かない。毎回 autoFit が文字ぶんへ戻してから広げ直すので値は
     毎フレーム同じに収束する）。ひし形・crosslane・グループ枠・部門枠は対象外。
     (b) allocatePorts の末尾の3rd pass では、すでに 10px 以上離れている辺は processFan の配置を
     そのまま尊重し（一直線優先・段違いトラックを壊さない）、詰まっている辺だけを 1st pass と同じ
     「相手の位置順に等間隔((i+1)/(n+1))」へ戻す。ピン留めがある辺は触らない。
     端を動かした線は、相手側の辺に1本しか来ておらずピン留めでもなければ「一直線」に整え直す
     （restraighten）＝v8.02 の一直線優先の狙いを保つ。
     当初は「まっすぐな線を固定し、曲がる線の端を14px押しのける」方式にしたが、接続位置が不揃いに
     見えるという指摘を受けて等間隔＋箱を広げる方式に改めた（ユーザー指示 2026-08-17）。
     ポートで直せない「無関係な2本が同じ座標に乗る」ケースは separateOverlaps で経路側を退避させる
     （内部の区間だけ・端の区間と手動経路/バスは動かさず相手としてだけ登録・箱を貫通しない位置を探す）。

  ④「自動経路がレーン境界の真上に乗る／重なると線の編集つまみを掴めない」
     orthoRoute の障害物はノード矩形だけで、A* の格子座標は「ノードの辺 ±PAD(9)」しか見ていない。
     レーン幅しだいでその track がちょうど境界に一致する。加えて、境界のドラッグ帯（幅8px×キャンバス
     全長の透明 rect）は最前面レイヤ g-dividers にあり、startLaneResize が先頭で stopPropagation するため、
     境界から±4pxに入った線とつまみは絶対に掴めなかった。
     対策＝(a) orthoRoute の内部に avoidLaneLines を足し、境界と平行な"内部の"区間が境界から
     LANE_EDGE_CLR(10px) 未満なら脇へ退避させる。端点（ノードの縁）に接する最初/最後の区間は動かさない
     ＝出入りの向きは保つ。候補は元の位置に近い順に試し、その区間と前後の接続区間の計3本すべてを
     clr() で検証し、どれも通らなければ元のまま（境界に乗るのは見栄えの問題、ノード貫通は重大）。
     clr の定義は MAXGRID の打ち切りより前へ移した（fallback にも掛けるため。obs にしか依存しないので同値）。
     (b) 当たり判定は、レイヤ順を変えずに「帯に穴をあける」方式にした。線の当たり判定を g-nodes より
     前面に出すと、線がノードの上を通る場面でノードのクリック・ドラッグを奪うため（回帰が大きい）。
     renderEdges が描いた実経路とつまみ座標を _edgeHitGeom に控え、renderDividers が境界ごとに
     その範囲を抜いた複数の rect を置く。ユーザー要望により、つまみだけでなく線そのものも優先する。

  ⑤「文字が2行以上になるとシェイプの中心がずれる」
     v8.10 の自動リサイズ autoFitNodeSize は n.w/n.h だけを書き換え、n.x/n.y を動かさない。SVG の矩形は
     左上基準なので箱は右と下へ伸び、2行目に入った瞬間に中心が半行ぶん下がる。同じ作りが
     calcMindNodeSize・note/state_detail の備考量調整・sections を持つ箱の3か所にもあった。
     対策＝setSizeKeepCenter を新設して4か所すべてを通す。大きさが変わらないときは何もしない（＝文字を
     変えない限り再描画で座標が流れない）。中心は丸めない＝行数が増減しても中心が少しずつ流れない。
     はみ出す場合だけ clampNodeIntoBounds で枠内へ寄せる。レーンの端に寄せた箱が幅いっぱいに広がるときは
     中心を保てないが、隣のレーンへ食い込むほうが実害が大きいので、はみ出さないことを優先する（既知の例外）。

  ⑥ 印刷（PDF出力）で上の枠線が左右より細い／消える
     expPDF は図面名・日付の白い帯を appendChild ＝最前面に置いており、帯の下端がちょうど y=0 にあるため、
     そこに乗るレーン外枠(1.5px)・見出し帯(1px)の上半分を白く塗りつぶしていた。左右は帯の外なので無傷＝
     「上下の枠線が左右と違う」。対策＝帯を insertBefore で最背面へ移す。あわせて、viewBox を x=0／下端に
     ぴったり合わせると、そこに乗る線は外側の半分が切り出し枠の外に出て 0.75px になるので、
     buildExportSvg と expPDF の viewBox を四辺 1px ずつ広げた（背景の白も同じだけ広げる）。
     ガントの分割 viewBox は改ページ計算が狂うので触らない（外枠 rect も持たない）。

  ⑦ 印刷に配置ガイドラインが写り込む
     render() は g-guides を消さない作りで（clearGuides を呼んだときだけ消える）、buildExportSvg は
     #diagram-svg を丸ごと clone するため、残っていたガイドがそのまま印刷・PNG・SVG に載っていた。
     対策＝clone から g-guides / g-replace-hl の中身と #prev-edge を落とす。画面側の状態には触らないので、
     書き出し後にガイドが消えたり点滅したりしない。

  ⑧ いちばん下のシェイプを画面の中央まで送れない
     スクロール範囲は #zoom-spacer の大きさ（SVG_W × SVG_H × zoom）ちょうどで、SVG_H は
     「いちばん下のシェイプの下端＋200px」しかない。SVG_H を増やして解決するのは不可＝レーンの背景も
     外枠も高さ SVG_H で、書き出し・印刷もこの高さを使うため印刷物に空のレーンが伸びる。
     対策＝applyZoom で #zoom-spacer にだけ「見えている大きさの半分」を足す。図の大きさは一切変えない。
     ウィンドウの大きさで変わるので resize でも applyZoom を呼ぶ。ガントは固定レイヤとスクロール量の
     読み替え（ganttStickyPt）が絡むので対象外。

  ⑨ レーン名をキャンバスの見出しのダブルクリックでも編集できるようにした（サイドバーと併存）
     要点は編集欄の置き場所。レーン見出しは #gstick-lane（position:sticky の重ね箱）の中の別SVGに
     描かれており、openSvgEditor が置く #diagram-svg は positioned でないため、そのままでは編集欄が
     必ず見出し帯の裏に隠れる。opts.host を足して重ね箱の中に置く＝見出しの図座標と表示位置が一致するので、
     固定表示中のズレ補正（ganttStickyPt 相当）も要らない。g-lane-hdr の中ではなく svg 直下に置くのは、
     renderLanes の innerHTML='' で編集中に消えるのを避けるため（buildExportSvg は g-lane-hdr だけを
     取り込むので書き出しにも混入しない）。
     もう1点、見出しを1回クリックして離すと mouseup が即 render し、renderLanes が見出しDOMを作り替えて
     2クリック目が別要素に当たるため dblclick がそもそも成立しなかった。ノードと同じ 220ms の遅延 render に
     変えた（openSvgEditor が冒頭でこのタイマーを解除するので、編集欄を開いた直後に消される事故は起きない）。
     確定時は snap()（S.lanes を直列化するので Undo が効く）と lanePanel()（サイドバー同期）を呼ぶ。
     サイドバー側の renameLane は oninput で毎打鍵呼ばれるため、そちらには snap を入れない（従来どおり）。

  ■ 既知の制約
  ・手動支点（曲線）の線とバス経路（樹状図/組織図）は交差ブリッジの対象外。
  ・曲がりの無い2点の直線どうしが無関係にぴったり同じ座標で重なる場合は退避しない（動かすと余計な
    曲がりが増え、参考PDFの「まっすぐ横」が崩れるため）。シェイプを共有する場合はポート段階で離れる。
  ・レーンの端ぎりぎりの箱は、文字が増えて幅いっぱいに広がると中心を保てない（レーン内優先）。
  ・ノードドラッグ中は交差ブリッジと重なり退避を走らせない（離すと確定 render で付く）。

  背景・目的:
    ユーザーからの改善要望13件。バグ修正だけでなく機能追加を含むため版を上げた。

  ■ なぜ v8.13追補②のL字が効かなかったのか（最重要）
    「別レーンへの接続を1回曲げにする」修正はコードとしては入っており、ポートの割り当て
    （allocatePorts の1st pass）も正しく「出口＝主軸の辺／入口＝源のある側の横辺」を選んでいた。
    効かなかったのは、実際の折れ線を作る orthoRoute の A* が exitSide/entrySide を
    スタブ位置の計算にしか使っておらず、探索そのものは「始点の進行方向」を知らないため。
    始点では pdir が未設定＝最初の一手はどちらへ曲がっても曲がりコストが0になり、
    近傍の列挙順（x+ が y+ より先）と厳密不等号（同コストは先着勝ち）だけで角が決まる。
    結果、縦モードでは必ず「横に走ってから縦に降りる」逆側の角が選ばれ、
    L字割当（出口=下辺／入口=左右辺）は 5点＝3回曲げの階段に化けていた。
    しかも修正前（入口=上辺）は末尾3点が同一xで潰れて4点＝2回曲げだったので、
    縦モードでは追補②によって曲がりが1回**増えて**いた。横モードでは横先行がそのまま
    L字になるため、実測では正しく見えていた＝これが発見を遅らせた。
    対策は2段構え。①出入りの軸が直交し2本ともどの箱も通らないなら A* を回さず即L字を返す
    （角は出口の軸を先に走る側＝lShapeClear が通行可否を確かめたのと同じ角）。
    ②A* の pdir[src] を出口の辺で初期化し、判定と経路が食い違わないようにする。
    あわせて lShapeClear の障害物条件を orthoRoute とそろえた（余白12→9px・始終点を
    内包する箱を除外）。従来は判定側だけが厳しく、通せるL字を先に却下していた。

  ■ 文字サイズと自動縮小の役割分担
    「シェイプの大きさに合わせて文字が小さくなってほしい」と「改行したら高さが伸びてほしい」は
    そのままでは相反する（どちらも行数が増える場面の話）。自分で入れた改行は「そう書きたかった」
    意思表示として必ず場所を確保し（＝箱が伸びる）、それを超えて自動で折り返された行が
    箱からあふれるときだけ文字を縮める、と切り分けた。下限は8px。
    手でリサイズしていない箱は従来どおり箱のほうが広がるので、既存の図は変わらない。
    fitNodeFontSize は状態を持たない純関数にした。ノードに一時キー（_fitFs 等）を持たせると
    JSON をそのまま保存する仕組みの都合で保存ファイルに混入するため。

  ■ 改行で中心がずれていた本当の原因（v8.13追補⑥で直したはずだった）
    setSizeKeepCenter 自体は正しかったが、抜け道が2つあった。
    ①説明有プロセスの備考は、編集確定時に n.h を直接代入していた。直後に render 側の
      備考ブロック（setSizeKeepCenter 経由）が走っても「同じ値なので何もしない」と素通りし、
      上端固定で下へ伸びた状態が残る。計算式が確定側と render 側で二重化していたのが根本で、
      render 側へ一本化して解消。
    ②レーン図では AUTO_W_MAX(260) がレーン幅(220)より大きく、日本語13〜18文字で必ず
      レーンからはみ出す。すると clampNodeIntoBounds が箱を端（lo+2）へ張り付け、
      setSizeKeepCenter は毎回「現在の x/y」から中心を読み直すため、壊れた中心が
      次の基準になって二度と戻らない（改行のたびに少しずつ下がって見える）。
      自動拡張の上限をレーンの実効幅までにしてクランプ自体を起こさないようにし、
      それでも大きい箱は端寄せでなくレーン中央そろえにして中心を保つようにした。

  ■ 編集中と確定後で見た目が違っていた理由
    編集欄は textarea（上詰め・行送りはブラウザ任せ・折り返しはCSS）、確定後は SVG に
    1行1要素で上下中央、という別々の組版だった。文字サイズ・行送り・折り返し幅・word-break を
    描画側の値に合わせる口（opts.fontPx/lineH/padX）を openSvgEditor に足して呼び出し側から渡す。
    枠線2px＋box-sizing のぶんがあるので、呼び出し側は padX=(描画側の左右余白-4)/2 を渡す。
    また Alt+Enter は inp.value を直接書き換えていて input イベントが出ないため、
    改行した瞬間は箱が追従せず次の1文字で一気に伸びていた。自分で dispatchEvent して解消。

  ■ 文字揃えが欄単位にできなかった理由
    「どの欄を編集中か」を覚えている場所がどこにも無く、確定用のクロージャの中にしか
    情報が無かった。さらに揃えボタンに preventDefault が無いため、押した瞬間に
    mousedown → 編集欄が blur → 確定 → svgEditorActive() が false、という順で
    必ずノード単位の設定が走っていた。_editTarget を新設し、ボタンでフォーカスを奪わない
    ようにして「編集中はその欄だけ／シェイプ選択中は全体」に分けた。

  ■ 旧ファイルのインポート方針（ユーザー指示 2026-08-18）
    インポートで引き継ぐのは「シェイプの配置・大きさ・文字・色・レーン構成・どこからどこへ
    繋がっているか」だけ。経路の決め方・接続点の割り当て・編集条件は今の版のものを必ず適用する。
    旧版には交差の見た目を整える手段が「支点を打って迂回させる」しか無く、その支点(waypoints)が
    残っているとその線は自動経路にもならず交差ブリッジの対象からも外れる（跨ぐ側にも
    跨がれる側にもならない）ため、線が途切れて見えていた。保存データに appVer を持たせ、
    旧版なら waypoints/orthoWps/midPos/fromPin/toPin をすべて落とす。今の版で保存した
    ファイルでは落とさない（そこでの手作業は本人の編集内容のため）。

  ■ 書類・データがレーンに連動しなかった理由
    doc と parallelogram が isFreeShape（レーンに属さないフリー配置）に分類されていたため、
    レーン単位で座標をずらす処理の対象から外れていた。分類から外して他のシェイプと同じ扱いにし、
    加えて nodeLaneIdx で「lid が無ければ実際の位置からレーンを判定する」ようにした
    （旧ファイルの書類・データは lid を持たないため、これが無いと読み込んだ図では連動しない）。
    レーン並べ替えでは、並べ替える前に判定を済ませる必要がある。後で判定するとレーンの位置だけ
    動いて座標は元のままなので、誤ったレーンに割り当たる。
    副次的に、書類・データが接続線の障害物として扱われるようになった（線が突き抜けなくなる）。

  ■ 複数レーンプロセスの厚み
    このシェイプの x/y/w/h は fromLid/toLid/mainPos/crossX/crossW から毎描画で計算し直される
    派生値で、厚みは SD.crosslane.h の固定値だった。汎用の8方向ハンドルで w/h を書いても
    次の描画で戻るため、ノードごとの thick を持たせ、辺の帯を掴んで変える方式にした。
    レーンの無い図種に置いた同じシェイプは fromLid を持たないただの矩形なので、
    そちらは逆に帯を出さず8方向ハンドルに任せる（掴むと laneX(undefined)=0 で
    左端へ飛ぶ不具合も、この切り分けで併せて解消）。

  ■ 既知の注意
  ・fitNodeFontSize は手でリサイズした箱（manualW）だけに効く。未リサイズの箱は従来どおり
    箱のほうが広がるため、文字は縮まない。
  ・接続線ラベルの折り返し幅は EDGE_LABEL_MAX_W=140 固定。文字サイズ変更の対象外。
  ・書き出し（PNG/Excel/SVG/テキスト）はダイアログを出さずブラウザ既定のダウンロード先へ保存する
    ままにした。書き出しのたびに保存先を尋ねると手数が増えるため。
